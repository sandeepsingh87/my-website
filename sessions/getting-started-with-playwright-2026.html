Playwright has quietly become the default choice for serious E2E test automation. Built by Microsoft and open-source since 2020, it has overtaken Cypress in adoption among enterprise teams — and for good reason. It is faster, supports all three major browser engines, handles modern authentication flows natively, and comes with a trace viewer that makes debugging failures genuinely pleasant.

This guide walks you through a complete, production-ready Playwright setup using TypeScript — from a blank folder to a structured framework with the Page Object Model, parallel execution, and a CI pipeline. Everything here is current to Playwright 1.58, the latest release line as of May 2026.

Playwright does not just run your tests — it tells you exactly why they failed, with a timeline, screenshots, network logs, and a step-by-step trace.

Why Playwright Over the Alternatives

Before diving into setup, it is worth understanding why Playwright is the right choice in 2026. The landscape of automation tools has consolidated significantly, and the choice largely comes down to three contenders.

FeaturePlaywrightCypressSelenium
Browser supportChromium, Firefox, WebKitChromium, Firefox, WebKit (limited)All, via WebDriver
ArchitectureDirect protocol (no WebDriver)In-browser executionWebDriver protocol
Auto-waitingBuilt-in, intelligentBuilt-in, limited scopeManual, explicit waits
Multi-tab / iFrameNative supportRestricted (same origin only)Supported with extra config
Trace & debuggingTrace Viewer, timeline, networkTime-travel debuggingLimited built-in tooling
Parallel executionBuilt-in, per-file by defaultRequires paid plan (Cypress Cloud)Manual configuration required

Selenium remains relevant for legacy enterprise environments where WebDriver compliance is a requirement. Cypress is excellent for frontend-focused teams running simple single-origin flows. But for a quality engineering team running a full E2E suite across authenticated journeys, APIs, and multiple browsers — Playwright is the clear choice.

Prerequisites

Before you begin, ensure the following are installed on your machine:

  • Node.js 18 or higher — Playwright 1.58 requires Node 18+. Run node --version to check.
  • VS Code — Install the official Playwright Test for VS Code extension for inline test running and debugging.
  • Git — For version control and CI integration.

Installation & Project Setup

1
Create your project folder
Create a new directory and initialise it with npm. The -y flag accepts all defaults.
terminal
bash 
mkdir my-playwright-project
cd my-playwright-project
npm init -y
2
Install Playwright with TypeScript
The init command installs everything and walks you through a setup wizard. Choose TypeScript when prompted.
terminal
bash 
npm init playwright@latest

# When prompted, select:
# - TypeScript
# - tests/ as your test directory
# - Yes to GitHub Actions workflow
# - Yes to install browsers
What gets installed

Playwright installs three browser engines: Chromium (~250MB), Firefox (~85MB), and WebKit (~65MB). These are isolated from your system browsers — your production Chrome is never touched.

3
Verify the setup works
Run the example tests that were generated during init. All should pass.
terminal
bash 
npx playwright test

# Open the HTML report after the run
npx playwright show-report

Configuring playwright.config.ts

The config file is the control centre of your Playwright suite. Here is a well-structured starting config that covers the most important settings for a professional setup:

playwright.config.ts
typescript 
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  // Test directory
  testDir: './tests',

  // Run all tests in parallel by default
  fullyParallel: true,

  // Fail CI if test.only is accidentally committed
  forbidOnly: !!process.env.CI,

  // Retry failed tests once in CI, not locally
  retries: process.env.CI ? 1 : 0,

  // Parallel workers — 50% of CPU cores
  workers: process.env.CI ? 2 : undefined,

  // HTML reporter with trace on first retry
  reporter: [['html'], ['list']],

  use: {
    // Base URL — change to your app URL
    baseURL: 'https://your-app.com',

    // Collect trace on first retry for debugging
    trace: 'on-first-retry',

    // Screenshot only on failure
    screenshot: 'only-on-failure',

    // Video on first retry
    video: 'on-first-retry',

    // Sensible timeouts
    actionTimeout: 10_000,
    navigationTimeout: 30_000,
  },

  // Test against three browsers
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
    // Mobile viewports
    { name: 'mobile-chrome', use: { ...devices['Pixel 5'] } },
  ],
});

Writing Good Locators

The single most common cause of flaky Playwright tests is poor locator strategy. Playwright's built-in locators are designed around how users actually interact with a page — not how the DOM is structured. This makes tests more resilient when the UI changes.

Avoid These Locator Patterns

XPath selectors, CSS class selectors (.btn-primary), and nth-child selectors are all implementation details that change often. A single UI refactor can silently break dozens of tests.

Prefer these built-in locators in this order of priority:

tests/locators-guide.ts
typescript 
// 1. By role — mirrors accessibility tree (BEST)
page.getByRole('button', { name: 'Submit' })
page.getByRole('textbox', { name: 'Email address' })
page.getByRole('link', { name: 'Sign in' })

// 2. By label — for form fields
page.getByLabel('Password')

// 3. By placeholder text
page.getByPlaceholder('Search transactions...')

// 4. By test ID — add data-testid to your HTML for stable anchors
page.getByTestId('send-money-btn')

// 5. By visible text — last resort for static content
page.getByText('Transaction confirmed')

// AVOID: fragile CSS / XPath selectors
// page.locator('.btn-submit-v2')      ← breaks on CSS rename
// page.locator('//div[3]/button[1]')  ← breaks on DOM change

Page Object Model

The Page Object Model (POM) is the most important structural pattern in E2E automation. Instead of writing page interactions directly in your test files, you encapsulate them in dedicated classes. This means when the UI changes, you update one file — not fifty tests.

Example: Login Page Object

pages/LoginPage.ts
typescript 
import { Page, Locator } from '@playwright/test';

export class LoginPage {
  private readonly page: Page;
  private readonly emailInput: Locator;
  private readonly passwordInput: Locator;
  private readonly signInButton: Locator;
  private readonly errorMessage: Locator;

  constructor(page: Page) {
    this.page = page;
    this.emailInput    = page.getByLabel('Email address');
    this.passwordInput = page.getByLabel('Password');
    this.signInButton  = page.getByRole('button', { name: 'Sign in' });
    this.errorMessage  = page.getByRole('alert');
  }

  async goto() {
    await this.page.goto('/login');
  }

  async login(email: string, password: string) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.signInButton.click();
  }

  async getErrorMessage(): Promise<string | null> {
    return this.errorMessage.textContent();
  }
}

Using the Page Object in a Test

tests/auth/login.spec.ts
typescript 
import { test, expect } from '@playwright/test';
import { LoginPage } from '../../pages/LoginPage';

test('successful login redirects to dashboard', async ({ page }) => {
  const loginPage = new LoginPage(page);

  await loginPage.goto();
  await loginPage.login('user@example.com', 'SecurePass123');

  await expect(page).toHaveURL('/dashboard');
  await expect(page.getByRole('heading', { name: 'Welcome back' })).toBeVisible();
});

test('invalid credentials shows error message', async ({ page }) => {
  const loginPage = new LoginPage(page);

  await loginPage.goto();
  await loginPage.login('wrong@example.com', 'wrongpassword');

  const error = await loginPage.getErrorMessage();
  await expect(error).toContain('Invalid credentials');
});

CI/CD with GitHub Actions

Playwright's init wizard generates a GitHub Actions workflow for you, but the default config is minimal. Here is a production-ready version that caches browsers, runs tests in parallel, and uploads the HTML report as an artifact:

.github/workflows/playwright.yml
yaml 
name: Playwright E2E Tests

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    timeout-minutes: 30
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: Install dependencies
        run: npm ci

            # Cache Playwright browsers — saves ~3 min per run
      - name: Cache Playwright browsers
        uses: actions/cache@v4
        with:
          path: ~/.cache/ms-playwright
          key: playwright-${{ hashFiles('package-lock.json') }}

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run Playwright tests
        run: npx playwright test

      - name: Upload test report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14
Pro Tip — Browser Caching

The cache step above is critical for CI performance. Without it, downloading all three browser engines on every run adds 3–5 minutes. With the cache keyed to package-lock.json, browsers only re-download when you upgrade Playwright.

What is New in Playwright 1.58

The 2026 release line has focused on debugging and developer experience rather than breaking API changes. The headline features in 1.58 are worth knowing if you are upgrading an existing suite.

  1. Timeline in HTML report. The new Speedboard tab shows a visual timeline of all test actions, making it straightforward to spot which step caused a slowdown or timeout without reading through logs line by line.
  2. Cmd/Ctrl+F search in Trace Viewer. You can now search inside code panels within the Trace Viewer and UI mode — a small but genuinely useful addition for large traces with many steps.
  3. System theme in UI mode. UI mode now respects your OS dark/light mode preference automatically.
  4. Removed: _react and _vue selectors. These experimental selectors were removed in 1.58. If your tests used _react= or _vue= selectors, migrate to getByRole or getByTestId before upgrading.
  5. Removed: devtools launch option. The devtools: true option in browserType.launch() has been removed. Use headed: true combined with manual DevTools if needed.

Key Best Practices

  • Never use page.waitForTimeout(). Hard-coded waits are the primary source of flakiness. Playwright's built-in auto-waiting handles element readiness — trust it.
  • Use browser contexts for isolation. Each test gets its own browser context by default. Never share state between tests — it creates order dependencies that are impossible to debug.
  • Use storageState for authenticated tests. Log in once, save the auth state to a file, and restore it in tests that need authentication. This removes login flows from every test and speeds up your suite significantly.
  • Keep test files focused. One spec file per feature area, not one file per test. Playwright runs files in parallel — large monolithic test files serialize unnecessarily.
  • Treat test code as production code. Code reviews, naming conventions, and refactoring apply equally to your test suite. Technical debt in test code compounds just as fast.
  • Use test.describe for grouping, not for shared state. beforeEach inside a describe block is fine. Shared mutable variables between tests in a describe are not.

Where to Go Next

With this foundation in place, the next areas to explore are API testing (Playwright supports full HTTP request testing without a browser), visual regression testing using expect(page).toHaveScreenshot(), and fixtures for managing shared setup across your test suite in a clean, composable way.

The official Playwright documentation is exceptionally well-written and kept current with every release. It is the best single reference for everything beyond the fundamentals covered here.
